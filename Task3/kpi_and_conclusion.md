# Метрики эксплуатации целевой архитектуры и итоговый вывод для CEO

## 1. Панель KPI эксплуатации целевой архитектуры

| Технический показатель (KPI) | Целевое значение метрики | Способ и инструмент замера (инструментарий / формула) | Бизнес-смысл — какую проблему решает замер |
| :--- | :--- | :--- | :--- |
| **Доступность транзакционного ядра (High Availability)** | **≥ 99.95%** в режиме 24/7/365 (допустимый простой не более ~4.38 часов в год). | **Инструмент:** Prometheus + Grafana + Blackbox Exporter (SLI/SLO дашборд на API Gateway).<br>**Формула:** `((Общее число запросов - Число ошибок 5xx) / Общее число запросов) × 100%` за расчётный период. | Минимизация финансовых потерь, простоев складов и курьеров при оформлении заказов, комплектации и отгрузках. |
| **Надёжность обработки платёжных уведомлений (Webhook Delivery Rate)** | **0% потерь** (100% успешная фиксация ответов/вебхуков от платёжных шлюзов банков). | **Инструмент:** Мониторинг очередей Kafka/RabbitMQ + сверка логов API Gateway и `Payment Service` в ELK/OpenSearch.<br>**Формула:** `(Число потерянных или отброшенных по 504 вебхуков / Общее число входящих вебхуков) × 100% = 0%` (контроль длины `Dead Letter Queue = 0`). | Исключение кассовых разрывов, зависших заказов и репутационных потерь, когда клиент оплатил доставку, но система потеряла статус из-за тайм-аута. |
| **Скорость доставки данных в аналитику (Analytics / DWH Latency)** | **≤ 5 секунд** (для 99-го перцентиля событий `p99`). | **Инструмент:** Метрики Debezium / Kafka Connect (`MilliSecondsBehindSource`) + сквозной замер в DWH.<br>**Формула:** `p99(T_dwh_ingested - T_db_committed) ≤ 5 сек`, где `T_db_committed` — время записи статуса в БД, а `T_dwh_ingested` — время появления записи в DWH холдинга. | Обеспечение сквозной прозрачности цепи поставок в реальном времени для руководства «Плюс Ритейл» и оперативного реагирования на отклонения SLA. |
| **Устойчивость к пиковой нагрузке: транзакционный контур (Order Throughput)** | **До 200 RPS** на создание заказов (масштаб **до 500 000 отправлений в сутки**) при времени ответа API `p95 ≤ 300 мс`. | **Инструмент:** Нагрузочное тестирование (k6 / Gatling) + APM-мониторинг (Prometheus / OpenTelemetry / Jaeger).<br>**Формула:** Замер количества успешно обработанных `POST /orders` в секунду без роста очереди и ошибок (`Error Rate < 0.05%`). | Гарантия десятикратного роста объёмов бизнеса (Scalability ×10) при подключении всех торговых сетей холдинга в сезонные пики распродаж. |
| **Устойчивость к пиковой нагрузке: потоковая телеметрия (IoT Ingestion Throughput)** | **До 3 000 RPS** на запись координат и телеметрии с датчиков транспорта при **0% потерь геоданных**. | **Инструмент:** Метрики `IoT Ingestion Service`, Kafka Broker (`MessagesInPerSec`, `Consumer Lag`) и ClickHouse.<br>**Формула:** Скорость записи потока в секунду при `Kafka Consumer Lag → 0` и полном отсутствии влияния на latency сервиса заказов. | Непрерывный контроль местоположения автопарка и условий перевозки грузов в реальном времени без риска обрушения складских и финансовых систем. |
| **Время восстановления и консистентность цепочки EDI (Saga Completion Time)** | **p99 ≤ 2 секунд** на шаг обработки EDI-документа (`ORDERS → DESADV → INVOIC`); **0 рассинхронизаций** (аномалий). | **Инструмент:** Распределённый трейсинг (Jaeger / OpenTelemetry) + бизнес-мониторинг статусов саг в Grafana.<br>**Формула:** Время прохождения событий между микросервисами и доля зависших/некомпенсированных транзакций (`= 0`). | Выполнение жёстких коммерческих SLA торговых сетей холдинга по электронному документообороту и исключение выставления некорректных счетов. |

## 2. Итоговый вывод для генерального директора Fast Cargo

> «Переход к целевому состоянию позволит компании избежать **критических операционных простоев из-за блокировок единой базы данных под лавиной IoT-телематики (3000 RPS), финансовых потерь от пропущенных банковских транзакций при тайм-аутах шлюза, срывов жёстких SLA по EDI-документообороту с торговыми сетями, а также многомиллионных оборотных штрафов за нарушение требований 152-ФЗ и стандарта PCI DSS при интеграции с CRM и платёжными системами холдинга**.
>
> За счёт внедрения **событийно-ориентированной микросервисной архитектуры (Event-Driven Architecture) на базе Open-Source стека с разделением данных по принципу Database-per-Service, потоковой CDC-репликацией в DWH и физической изоляцией контуров персональных данных, платежей и высоконагруженной телеметрии** бизнес получит **гарантированную пропускную способность до 500 000 отправлений в сутки (200 RPS на создание заказов), доступность ядра системы на уровне не ниже 99.95%, 0% потерь платёжных уведомлений и доставку сквозной аналитики в DWH холдинга менее чем за 5 секунд**, что полностью окупит инвестиции в трансформацию ландшафта и гарантирует стабильную работу при росте нагрузок в десять раз».
